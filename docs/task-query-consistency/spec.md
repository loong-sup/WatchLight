# 关注任务查询一致性修复 Spec

## 背景

飞书中的自然语言任务创建与普通大模型对话目前走两条独立链路：创建和确认由确定性的任务流程处理并写入关注任务数据库，后续的“目前创建了哪些任务”则进入通用大模型。通用大模型没有访问关注任务数据库的能力，只能看到尚未接通的会话和记忆查询结果，因此会把“未查到会话或记忆”错误解释成“没有创建任务”。此外，被任务流程提前处理的消息没有写入同一会话历史，进一步放大了上下文断裂。

## 目标

- 用户在飞书或 Web 对话中查询关注任务时，得到当前渠道身份对应用户的真实持久化任务。
- 常见任务列表问法不依赖模型自由判断，结果稳定且可验证。
- 通用大模型能够通过受用户身份约束的只读能力查询关注任务，覆盖非固定问法。
- 自然语言创建、补充、确认和确定性查询的问答进入同一会话历史，后续追问能够看到真实交互上下文。
- 任何查询失败或缺少身份时均不得回答“系统中没有任务”。

## 功能需求

- F1：系统必须识别“目前有哪些任务”“查看已创建任务”“我之前创建的任务”等常见任务列表意图，并直接读取关注任务持久化存储。
- F2：任务列表必须只返回当前已解析用户有权访问且未删除的任务；至少展示关注目标、状态、执行频率和通知渠道。
- F3：当前用户没有任务时，系统必须明确回答“当前没有关注任务”；查询异常时必须明确回答查询失败，不得把异常等同为空列表。
- F4：通用大模型必须获得只读的关注任务列表能力，以支持未命中确定性意图规则的自然语言追问；调用时必须使用网关解析出的规范用户身份，模型不得自行提供或覆盖用户身份。
- F5：通过飞书或 Web 对话被任务流程提前处理的用户消息和系统回复，必须写入该渠道对应的会话历史，包括创建、补充、确认和列表查询。
- F6：系统提示必须要求模型仅依据关注任务查询结果陈述任务是否存在，不得使用会话列表、记忆库或未执行的“查询意图”代替任务查询结果。

## 非功能需求

- N1：任务查询必须沿用现有按用户隔离的存储访问方式，缺少规范用户身份时拒绝执行。
- N2：列表查询为只读操作，不得修改任务、版本或执行计划。
- N3：现有自然语言任务创建、确认、调度和通知行为保持兼容。
- N4：飞书远程消息工具权限仅新增关注任务只读查询，不扩大到本地文件、Shell 或任务写操作。
- N5：确定性查询回复应在一次本地数据库访问内完成，不依赖外部模型或网络服务。

## 不做的事

- 本次不新增通过自然语言修改、暂停、恢复或删除任务的能力。
- 本次不改变任务调度频率、采集、分析和通知逻辑。
- 本次不实现语义记忆库，也不把关注任务复制到记忆库。
- 本次不处理跨渠道身份自动合并；仍沿用现有显式身份绑定规则。
- 本次不清理当前数据库中可能因重复确认或重复创建产生的既有任务。

## 验收标准

- AC1：飞书用户完成任务创建和确认后询问“目前创建了哪些任务”，回复中出现刚创建任务的目标、`active` 对应的人类可读状态、每天执行和飞书通知，且不再回答“没有任务”。
- AC2：同一用户存在多个任务时全部列出；没有任务时返回明确的空列表提示；数据库查询异常时返回查询失败提示。
- AC3：两个不同用户分别查询时只能看到各自任务，无法通过请求参数或模型工具参数读取另一用户任务。
- AC4：未命中固定列表问法的任务查询可由通用大模型调用只读任务能力，工具结果来自关注任务数据库并携带稳定的结构化字段。
- AC5：创建、补充、确认、列表查询及对应回复均能在同一个渠道会话历史中按顺序读取。
- AC6：现有自然语言创建测试、身份隔离测试、任务存储测试和调度测试继续通过。
